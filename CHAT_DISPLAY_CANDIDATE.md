# Detached display and receipt candidate

This is **developer-only**. The tested player still uses paired IPC 2 and has no unread badge. `dev/chat_display_candidate.py` and `dev/java/syx/assistant/candidate/` are not packaged/imported by production. They use disposable histories and detached text; no game API, provider, watcher, normal history migration or automatic acknowledgement is implemented.

The proposed IPC 3 display carries an epoch/frame UUID, selected chat/current runtime, explicit count availability, complete global Pro unread total, bounded per-chat counts, plain UTF-8 text encoded as canonical base64, and individual eligible final-reply provenance. Global counts apply Pro/API/model filters before scan limits; 100 chat-count rows can be explicitly partial while the complete global total remains available. Unknown counts are `?`, never zero. Only completed, nonblank final assistant events count. Existing history initialization remains explicit and transactional; it baselines already completed replies without marking pending replies read.

Display frames are at most 240,000 ASCII bytes, show the latest 100 original events plus an earlier-history marker, and disclose wire omissions. Removed text has no receipt eligibility. Each reply record identifies its exact preview row, event UUID, turn UUID, original observed session and stored payload SHA-256. Current attachment/runtime is separate from historical event provenance. No model text can create framing fields. Unchanged refreshes reuse the frame until expiry; eight issued frames survive at most 30 monotonic seconds. A helper restart changes the epoch. Completed-event scans retain the 10,000-row/2-MiB limits; exceeding a budget refuses a complete result instead of returning partial counts.

Receipts use a separate, bounded 16-KiB request with 1..100 exact issued event IDs from one original session. The broker requires actual caller-supplied fresh matching MCP runtime presence, an unexpired issued frame, matching chat/runtime/epoch and unchanged payload hashes checked inside the receipt transaction. Duplicate receipts are idempotent; invalid batches roll back wholly. The request UUID is echoed by the detached broker. No file transport, coordinator response watcher, Send/Stop coupling or native integration exists yet. A client must retain pending state until a matching applied response, and must not infer successful persistence from a write alone.

`DisplayFrame.java` rejects malformed/duplicate/unknown fields, noncanonical UUIDs/counts/base64, invalid UTF-8, inconsistent totals, out-of-bounds provenance and protocol mismatch. `DisplayCoverage.java` is a conservative pure policy: every wrapped segment of an eligible reply must be rendered in **one** paint under an explicitly established VISIBLE gate. Closed, hidden, other-chat, obscured and unknown gates never qualify. Partial paints do not accumulate across scrolling; frame/epoch/chat/runtime/layout mismatch and cancellation invalidate evidence. Layout metadata is bounded to 100 events/4,096 segments. Oversized answers can remain unread under this policy; an explicit player read action or different reviewed policy remains a design decision. Returning candidate IDs does not persist a receipt or prove native visibility.

Unchanged display refreshes avoid repeating event scans. The cache combines own-connection change count with same-connection [SQLite data_version](https://www.sqlite.org/pragma.html#pragma_data_version), which detects other connections' committed changes. Tests cover a second local writer. This is a finite cache check, not general concurrent schema/writer acceptance.

[Validation](CHAT_DISPLAY_CANDIDATE_VALIDATION.json) records 394 passing offline tests, including 38 new Python/Java test cases beyond the prior 356-test player checkpoint. The cross-language case includes seven accepted and malformed rejected frame corpora, Java-created historical-session receipts applied to disposable Python SQLite history, and pure wrapped-segment policy checks. The earlier receipt report retains its original scope. No new paid/native/player acceptance is implied by these offline tests.

[Native visibility findings](CHAT_VISIBILITY_BOUNDARY.md) establish why activated/rendered/empty-tooltip checks alone cannot clear unread state.
