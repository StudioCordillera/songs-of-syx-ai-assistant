# Selected-subject absence and selection transitions

The developer fixture `dev/run_selected_resident_absence.py` extends the [selected housed-worker query](SELECTED_RESIDENT_QUERY.md) with public subject-panel removal. It uses the unchanged production player to collect four original observations in one paused copied-city callback: no subject, first housed worker, second housed worker, no subject. It serves those original observations through a separate private MCP mailbox, preserving snapshot IDs, timestamps, sessions, game ticks and UI context.

The absence case matters when a player asks about a person after closing their subject panel. The ordinary entity prefix can still contain people while `/selected_subject` and the UI-context subject are null. The specific three-join example refuses its missing selection precondition with the existing generic “Join requires objects and a non-conflicting alias” error; improving that player-facing wording remains separate. It does not substitute the first cached entity, silently reuse the previously selected person or report a homeless person. Publishing each next observation rejects the preceding snapshot pin. Panel removal alone does not invalidate an unrefreshed pin: old data remains an older observation until collection publishes a replacement.

## Public source boundary

The test calls public `VIEW.s().panels.clear()` before and after the two existing `showSingle` selections, then checks public `subjects.current()` immediately. In the shipped source, `ISidePanels.clear()` removes the added panels; `UISubject.showing()` returns a subject only when its own panel is added, and `UISubjects.current()` delegates to that result. No private subject field or UI panel handle is inspected. The compiled fixture and direct checks establish this finite route against the pinned installed game, not a documented stable scripting contract.

The fixture only changes presentation and pause state inside the disposable copied profile. It does not reassign housing/workplaces, create entities, request a save, send native input, capture screenshots or call a provider. Public panel removal is not a physical close-button test, visible/rendered UI proof, game-menu/unload guarantee or acceptance of all subject lifecycle changes. All four captures occur within one callback; they are not observations separated by natural play or a concurrent live MCP workload.

## Reproduction and evidence

Run `dev/run_selected_resident_absence.py` with the licensed game, copied save, Java and JDK arguments in [CONTRIBUTING.md](CONTRIBUTING.md), under an appropriate isolated display. The existing runner acquires the shared native fixture lock, validates player/game/source hashes, restores the copied mod and checks copied-save integrity. Original observations and native logs stay private. Normal simulation may write automatic saves inside the disposable profile; no engine-wide no-save claim is made.

[The exact-build report](SELECTED_RESIDENT_ABSENCE_VALIDATION.json) records four original observations, nineteen actual MCP calls (eight reused positive-query checks and eleven transition checks), two explicit absence refusals, source checksums and clean zero-exit/restoration checks. Seven existing synthetic query/precondition regressions also pass. No full-suite or player-release run is relabeled as fresh. The earlier two-subject report remains historical with its original scenario/checksums. The latest and previous tested downloads, production Java/Python and release evidence remain unchanged. Missing recorded workplace/housing, larger-city/cap/fault/unload behavior and native physical interaction remain separate gaps.
