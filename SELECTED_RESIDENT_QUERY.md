# Selected housed-worker query — existing read-only exports

[selected-resident-query-example.json](selected-resident-query-example.json) uses the existing three-join budget to connect the underlying selected subject, recorded home relationships, observed home configuration and a nullable cached employment record. It projects selected identity, home service/assignment coordinates, configured capacity, recorded workplace ID and the observed staffing record. It does not return the subject's complete stat list or the entire snapshot.

Ask `game_status` and `describe_game_fields` first. This example requires an available selected subject with a recorded workplace and available city housing tables. Its first two joins are inner joins; its employment join is left/optional. Use one `select_game_state` request, adding the original `expected_snapshot_id` when intentionally pinning a previously inspected observation. `include_ui_context` preserves that observation's context. Publishing a new observation that reflects a selection change invalidates the old snapshot pin. Selection alone does not invalidate it immediately: until refresh the old pin still identifies the old selected-subject observation. Never combine that older subject data with newer home rows.

## Meaning and qualified absence

Room IDs join the same observation's registry slots; person IDs join recorded/resolved roster IDs. Neither is permanent identity. The home coordinates identify recorded assignment/service tiles, while employment coordinates are stored room anchors. These values establish no current physical presence, usable vacancy, eligibility, path/search distance, commute time or optimum layout. The subject panel may be obscured or hidden: this is underlying selection context, not display/visibility proof.

A selected person missing from bounded home rows yields zero inner-join matches. Inspect all four source metadata entries and their collection/failure/truncation qualifiers; zero matches do not establish homelessness or a citywide census. Missing cached employment remains `observed_workplace=null` while the person's recorded workplace ID remains available. This does not establish unemployment. Duplicate recorded home links remain duplicate result rows rather than being silently deduplicated.

No selected subject, a missing recorded workplace path or unavailable housing tables can refuse this example. Those are declared preconditions, not cases repaired with empty/zero data. Use separate supported observations for an unemployed/unhoused subject rather than changing the meaning of this query. These joins do not combine independently observed live entity pages or historical captures with the current cached housing state.

## Native and synthetic evidence

[Native validation](SELECTED_RESIDENT_QUERY_VALIDATION.json) pins two naturally housed employed subjects selected through the existing public subject UI in one paused copied-city callback. Direct public home/assignment/workplace/staffing values agree with the production exports and eight actual MCP calls. Checks include the authored query, eight observed field paths, all four source entries, original UI/snapshot identity, raw home-assignment values and refusal of the earlier pin after the second selection. The raw observations remain private and are served unchanged through a separate retained-observation mailbox.

Seven synthetic cases in `test_selected_resident_query.py` cover exact projection/source metadata, nullable missing employment, qualified missing home prefix, duplicate links and refused selection/workplace/housing preconditions. They do not establish native cap/fault behavior. The full offline suite passes 630 tests; the current player retains its separately recorded release evidence. This is a finite same-callback/retained-original check, not concurrent live servicing, all selected subjects/scenes or a larger-city performance benchmark.
