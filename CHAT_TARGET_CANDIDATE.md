# Next-message target evidence candidate

`dev/chat_target_candidate.py` begins UX-06 by attaching explicit existing capture pages to individual chat drafts. This is developer-only, not imported or packaged by the player. It adds no game readers, target picker, native chips, MCP tool, provider dispatch or gameplay commands. The standalone browser chips remain simulated.

The adapter accepts exactly the three existing entity, tile and regional-output capture pools belonging to one advisor. It calls their fixed public Python `read` methods; there is no arbitrary reader dispatch. This original local adapter expects those pools in the same process. A later [async MCP transport candidate](CHAT_TARGET_TRANSPORT.md) reuses its detached core across an existing stdio connection; neither adapter is wired into the player. The current coordinator and stdio MCP do **not** share Python objects, so production integration requires a separately bounded MCP/IPC transport and owned capture lifetime. Server-local tokens cannot simply be copied to another MCP process.

A staged attachment contains the original capture UUID, runtime, game version, tick/time, scene, scope, selection/fields, warning/consistency metadata, explicit row offset/limit, returned rows and next offset. A SHA-256 pins that exact observation page. Original unknown/null fields survive unchanged. This is evidence from a selected page, not an entity handle, current UI selection, permanent room/world ID, complete capture dump or executable target. Entity metadata retains what the existing reader exposes; it does not invent an original request ID absent from that metadata.

Before preparation, every page is read again from encoded retention, with fresh loaded non-demo status required. The runtime/version and complete exported scene object must still match; unsupported/unknown scene labels refuse. A final status check catches observed changes between separate pool reads. Stored bytes must agree with the preview. Expiry, eviction, missing/wrong-pool tokens, changed observation or lifecycle mismatch refuse the **entire** envelope. Drafts remain available for historical inspection/removal on failure. An initial runtime/version/scene mismatch is refused before reading the pools. The production pools independently prune expired tokens and invalidate on runtime/version changes; a racing read can still remove backing evidence. Draft preservation is not a guarantee that shared capture retention remains unchanged. These are recent-export checks, with the production freshness window; they cannot detect every transition between observations or guarantee that the game stays unchanged after preparation.

Independent captures retain separate original ticks/times. Re-reading pages never updates their rows, freezes the simulation or creates a global transaction. The text notice labels them historical. Even within one runtime, scene IDs/room indexes may be reused. The candidate never turns retained coordinates or IDs into gameplay action authority. Rich target identity, actual picker eligibility and reference-passage attachments need separate work.

Bounds: eight attachments per chat, 100 draft chats, explicit pages of 1..100 rows, and 32 KiB UTF-8 for the complete outgoing evidence envelope including provenance. No silent eviction, truncation or clearing occurs. Duplicate and overlapping pages from one capture are refused. A preview includes remaining retention measured at staging and a warning that this is not current liveness; earlier eviction/restart can already have invalidated it. Empty prepares explicitly return `has_attachments=false` for the optional-attachment case. Existing capture pools still enforce their own independent three-token/120-second retention and byte/scan/row budgets. Long composer delays can expire a target; a future UI must offer an explicit new selection rather than silently recapture different evidence.

`prepare` returns detached JSON evidence only; it neither sends nor consumes a draft. A future coordinator must preserve accepted attachment IDs and original provenance in the durable turn, revalidate after asynchronous waits, handle duplicate sends and only clear the exact accepted chips on queue acknowledgement. Prompt/data separation, cancellation/retry, actual transport cost and native affordances remain acceptance gates. Non-finite numbers refuse with an actionable narrowing message; the adapter does not invent a replacement value. No normal history migration, save, provider call, credential access or native game fixture runs in these tests.

`test_chat_target_candidate.py` exercises the actual production encoded pools with synthetic game-read payloads: provenance/unknown retention, separate observations, immutable response copies, chat isolation, duplicate/wrong-chat removal, stale/unloaded/demo/runtime/version/scene refusals, same-view scene changes, token expiry/restart/wrong-pool rejection, mid-prepare observed switches, mutation detection and atomic per-page/aggregate/chat limits. [Evidence](CHAT_TARGET_CANDIDATE_VALIDATION.json) pins source and suite scope. These finite offline checks are not native/MCP transport or player acceptance.

## Completed local Claude review

A bounded tool-free local Claude Code Opus/high review completed on `claude-opus-5-5` in 154661 ms, with four reported turns. It reviewed the initial candidate and synthetic tests, not the final follow-up source or native game. We accepted the retention-visibility concern with an explicitly staged-time hint, added eviction/recovery regressions, made full-scene/unknown-scene refusal safe, added actionable non-finite rejection and overlapping-page refusal, and flagged empty optional preparations. The initial scene fix/full-scene check was independently underway before the review returned. We retained production capture invalidation semantics and documented racing pool mutation instead of adding private/non-destructive bypasses. Invocation and final-source hashes are in the evidence report. No inference provider expansion, credits purchase or limit bypass occurred; private CLI streams/internal thinking are not published.
