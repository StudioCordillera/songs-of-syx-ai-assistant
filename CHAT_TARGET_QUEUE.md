# Durable target-backed question acceptance candidate

`dev/chat_target_queue.py` connects an exact send intent to the existing [MCP target adapter](CHAT_TARGET_TRANSPORT.md), then records the question and original selected evidence together in disposable real `ChatStore` histories. It is **developer-only**: no native picker/chip/send protocol, player import, provider dispatch or normal-history migration is shipped. A `queued` turn means accepted into history, not sent to DeepSeek or answered. Production `Conversation.run` currently begins its own turn and cannot consume these already-created turns without a reviewed integration.

The owned helper receives chat/request/turn/runtime IDs, question text and the exact ordered list of attachment UUIDs. The request is copied before any await. It obtains strict preparation from the same long-lived MCP session, including final recent-export admission metadata; an empty target list still checks the expected runtime. UI requests cannot submit a raw evidence envelope through this path. Unknown/changed selections refuse rather than silently include newer chips. Snapshot IDs are opaque exporter observation strings (`session:sequence` in the paired source), not UUIDs or permanent world IDs.

One `BEGIN IMMEDIATE` transaction rechecks the request, current chat attachment, explicit simple Pro route, pending/running-turn exclusion and a two-second local preparation lease. It conservatively refuses export timestamps outside -5..30 seconds, matching the current default freshness boundary. It inserts the `queued` turn, user event, `target_evidence` event and immutable accepted-envelope record together. Any conflict, failed event insert, database lock refusal or validation failure leaves no partial new turn/events/queue record. `_event` does direct SQL without committing; no `ChatStore` method with its own transaction is nested. The shared helper thread may wait on SQLite's configured busy timeout; this is outside the game process and is not helper/UI latency acceptance.

Evidence stays within 32 KiB, eight targets, original capture/session/version/scene/tick/time and page hash. The envelope/item/admission/retention-hint keys are allowlisted, and the whole accepted envelope has an independent hash. Known credentials/private fields refuse rather than silently redact and change the approved evidence. Question text has a total 8000-character bound and known-credential checks. A lost acknowledgement can retrieve the original acceptance after restart or capture expiry; that receipt is explicitly not fresh target authority. Reusing its request UUID with different chat/turn/runtime/text/target IDs refuses. If a concurrent exact call commits and clears its chips while another awaits MCP, the latter rechecks durable acceptance instead of mistaking the changed draft for a new send.

Acceptance does not clear the composer. Separate acknowledgement reloads the committed original record and clears only its exact attachment UUID/hash pairs. Missing old IDs are idempotent; newly added or restaged chips survive, including after restart or chat attachment changes. No native question-text clearing is implemented. A wrong/changed hash refuses the whole clear batch. Public receipt/evidence reads refuse an open caller transaction, so uncommitted data cannot masquerade as durable acceptance. These guarantees concern owned APIs, not an adversary with arbitrary write access to the SQLite file.

Explicit initialization preserves base `user_version=1` and independently versions `target_queue` in `syx_ux_schema`. It adds one cascade-linked queue table and a pending-chat index; it does not scan/rewrite existing event history. Receipt and queue extensions can now initialize in either order; the earlier receipt candidate no longer mistakes another component's registry row for its own version. Unknown versions/unversioned owned tables refuse. Base `ChatStore(recover=True)` retains a queued question without starting work. Explicit queued-only cancellation preserves accepted evidence, marks the turn cancelled and permits a new deliberate request. A future dispatch lane must establish a separate durable claim, fresh runtime admission, provider-loop handoff, cancellation/failure and uncertain-network recovery. No paid exactly-once or automatic replay guarantee is claimed.

`test_chat_target_queue.py` checks atomic rollback after partial inserts, exact retries, concurrent lost-ack races, credential and provenance refusal, lock/lease/runtime/selection bounds, restart, cancellation, no false unread completion, foreign-key deletion, both extension orders and actual latest/previous bundled-store compatibility. Real stdio tests use the production MCP server with synthetic capture readers. `dev/verify_tiles.py` additionally validates durable acceptance of two public-getter-matched tile rows through actual MCP and the unchanged published JAR, copied private history restart, exact replay and old-ack preservation of a restaged target. Normal saves and histories are untouched. [Evidence](CHAT_TARGET_QUEUE_VALIDATION.json) pins final sources, original bundle hashes, zero inference and clean copied-mod/save restoration. This is finite tile/backend evidence, not native client or native entity/regional acceptance.

## Completed local Claude review

A bounded local CLI review completed on `claude-opus-5-5` at high effort. Its concurrent exact-retry concern produced a new real-stdio interleaving regression and durable relookup; its extra-field concern produced strict structural allowlists. The text-secret concern was not an existing leak: `ChatStore.clean(text)` already replaces registered secret values and the original negative case passed. We retained that protection and added an explicit substring guard for clarity. The mutable-list concern was resolved by consistently passing the frozen intent. Independent checks also added committed-only receipt reads and receipt/queue schema coexistence. The critique covered its pinned initial queue source, not the final follow-up code or production dispatch. [CLI metadata](CLAUDE_UX_COLLABORATION.json) records the actual outcome; no credits, account changes or limit bypass occurred.

A later [developer dispatch follow-up](CHAT_TARGET_DISPATCH.md) now provides an explicit durable claim/store seam into the unchanged loop; this original queue module and its earlier report retain their acceptance-only scope. Production still does not import either candidate.
