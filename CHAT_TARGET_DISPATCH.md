# Explicit accepted-question dispatch candidate

`dev/chat_target_dispatch.py` connects the [durable target queue](CHAT_TARGET_QUEUE.md) to the **unchanged production `Conversation` loop** through a fixed owned-store seam. It is developer-only, requires explicit initialization on a disposable history, and is not imported by the player. There is no worker, new MCP tool, provider/key configuration, normal-history migration or native picker/send control. The playable download remains unchanged.

An explicit `run(request)` freezes and verifies the original accepted intent. It retrieves the original hash-pinned evidence, obtains fresh/live MCP admission using the caller-owned initialized session, and requires the same runtime, version and full scene. It never recaptures or requires the original retained token to remain alive. Historical selected rows stay labeled as untrusted observation data, with original session/tick/time/scene and uncertainty; they are not instructions, fresh state or gameplay authority. The unchanged loop performs its own fresh matching-runtime recheck before inference and before selective tool reads. These are sequential observations, not a global transaction over the game.

The fixed `_ClaimStore` forwards normal event, cleanup and terminal-status operations to our own store. Only `begin` is replaced: one `BEGIN IMMEDIATE` checks the exact intent/evidence, current Pro route/attachment, two-second preparation lease and recent export timestamp, then transitions `queued` to `running`, inserts a unique durable request claim and records `dispatch_claimed`. Failure rolls everything back to queued; a claim is committed before the loop can create a provider or call inference. The original user and target-evidence events are retained once; augmented model text is not inserted as a second user event. A currently registered credential found in older accepted data refuses dispatch before claim; newly registered secrets are checked again before handing text to the loop. Each invocation deliberately uses a fresh in-memory conversation context and the loop's bounded historical-text policy. Accepted targets enter a user-data message, never fabricated assistant/tool continuation.

One claimed request can start at most one workflow through this owned API, even across two local coordinators or restart. A workflow still permits the existing eight provider rounds/sixteen tool calls. A claim does **not** prove any network delivery, billing outcome or exactly-once provider execution. Cancellation/disconnection after claim can leave the remote outcome unknown. The existing loop records failed/cancelled terminal status and closes its provider; abrupt process death leaves a running turn that explicit single-owner startup recovery marks interrupted. Every claimed request remains refused on retry, including failed, cancelled, interrupted and completed turns. There is no automatic replay or lease-stealing. The player would need an explicit new request to try again, with clear unknown-outcome wording; that control is not implemented. `recover=True` must never be used against a live coordinator.

Before claim, admission failure/cancellation leaves the accepted request queued and makes no inference call. Queued-only cancellation remains available through the queue. Chip acknowledgement remains independent; dispatch never clears current drafts or uses newer selections. The acceptance receipt's `provider_dispatch: not_implemented` describes that earlier queue-only acceptance response, not a live dispatch-status query. Read durable turn/claim state for this developer follow-up. No native request/claim/stop response protocol or unread display integration is supplied.

`target_dispatch=1` is a separately versioned extension in the shared registry, retaining base history version 1 and `target_queue=1`. Its request/claim table cascades when the parent chat is deleted. Unknown versions and unversioned tables refuse. The adapter/store helper methods are owned project code, not private game APIs; the production game boundary and eighteen read-only tools are unchanged. This seam is a testable bridge toward integration, not a selected public plugin ABI. The coordinator must own the history and task lifetime; mixing this developer lane with independent legacy writers is not supported.

`test_chat_target_dispatch.py` exercises the real stdio production MCP server with synthetic readers and fake providers: original selected evidence and selective follow-up rounds, atomic rollback, concurrent claims, frozen caller IDs, pre/post-claim failures, cancellation, unknown remote outcome, restart refusal, schema refusal and cascading deletion. `dev/verify_tiles.py` additionally uses the copied city and unchanged player JAR, then explicitly hands two getter-matched original tile rows to a fake provider **after the original retained token has been evicted**. It checks completed status, one original question, refusal of repeat dispatch, preservation of newer chips and no tile-mailbox write. No real Pro request is made. [Evidence](CHAT_TARGET_DISPATCH_VALIDATION.json) pins exact sources and finite scopes; native player controls and real provider acceptance remain open.

## Completed Claude Code peer review

A bounded tool-free local Opus/high review completed on actual `claude-opus-5-5` (78788 ms, one reported turn). We added a claim-time existing-running-turn check and regression from its mutual-exclusion concern. Queue admission already excludes multiple accepted queued/running turns, and the added guard also refuses a pre-existing legacy running turn. A legacy writer that ignores the claim protocol can still start later; concurrent independent legacy/native writers remain outside this candidate's single-coordinator contract.

Two other concerns were conditional rather than demonstrated defects. The monotonic lease is checked **after SQLite acquires `BEGIN IMMEDIATE`**; database contention or synchronous work can consume its two seconds despite no intervening await, and the expired-lease test refuses. The wall-age check deliberately follows this same-device helper/exporter boundary; remote hosts or unsynchronized clocks are not supported. The queue has no prune/expiry API: accepted records remain after capture eviction, and claims persist across terminal status/restart. Cascading explicit chat deletion intentionally removes private history and ends that record's refusal lifetime. There is no claim of an eternal/global request-ID ledger after history deletion; a future queue-pruning design must retain claims or use a restrictive foreign key. No pruning feature was added. Final guard follow-up is independently tested, not re-reviewed by Claude. [Invocation metadata](CLAUDE_UX_COLLABORATION.json) pins the earlier reviewed source separately from final code; no credits purchased or limits bypassed.
