# Owned accepted-question tasks and Stop candidate

`dev/chat_target_tasks.py` adds an explicit helper task owner around the existing [admission/queue](CHAT_TARGET_QUEUE.md) and [dispatch seam](CHAT_TARGET_DISPATCH.md). It is developer-only: no native button, request-file protocol, watcher, polling worker, normal-history migration, new MCP tool or gameplay command is shipped. The production code and both playable ZIPs remain unchanged. The earlier [real Pro backend check](CHAT_TARGET_DISPATCH_PRO_VALIDATION.json) retains its original source and scope; this newer task owner uses fake providers in its finite tests.

One caller owns one event loop, one initialized admission/dispatch queue and adapter, and the MCP/history lifetime. Explicit `start(request)` freezes the full original intent, serializes admission and registers one task immediately after durable acceptance, with no intervening await. Exact retries return the original view; a durable claim is never relaunched. Up to eight owned active tasks are admitted, counting pending cleanup. Overload refuses before new acceptance and leaves drafts alone. There is no automatic replay after reconnect, restart or failure. A before-claim failure can leave a queued question; only a new explicit start can attempt that unclaimed question again. An accepted record is not proof of inference or delivery.

`stop(request)` validates the exact original intent and cancels only the matching owned task. An immediate Stop before the coroutine starts first cancels the durable queued turn, so no provider runs. During inference it sends one cancellation request; repeated Stop cannot cancel provider cleanup again. A final completed answer stays completed while cleanup finishes. A queued before-claim failure can also be cancelled while its ownership remains in the bounded recent cache, including the task-done/before-callback interval. Unowned requests are observed without cancelling another coordinator. Recent ownership is an in-memory bounded cache, not a durable cross-restart authority; an older unowned queued record needs an explicitly reviewed queue-cancellation path in the eventual coordinator protocol.

Views distinguish durable turn status, **owned** task activity, pending cleanup and a conservative unknown remote outcome. Local `failed`/`cancelled` status does not prove that a remote server rejected a request, stopped generating or avoided billing. Claimed non-completed turns retain `remote_outcome_unknown=true`, even after local cleanup. Views and the last 100 attempt summaries contain fixed metadata/digests, never provider reply text, raw exception strings or retained tracebacks. Completed tasks are removed from the active map and their exceptions consumed. This is no global/exactly-once remote-delivery guarantee.

Admission itself is an awaited request, separate from accepted-task ownership: cancel its caller task to abort pending MCP preparation. The future native protocol must connect pending-request cancellation and accepted-task Stop to one understandable user flow. No such protocol or native Stop control is provided here. There is no scheduling gap after the owned admission coroutine commits/returns and before task registration in this single event loop; arbitrary foreign admission wrappers/writers are not supported.

`close()` is coordinator shutdown, **not panel hide/close**: closing the game chat menu must leave these tasks running. It first rejects new work, serializes with in-flight bounded admission and cancels accepted work that finishes admission after closure begins. It requests Stop for each owned task and observes cleanup for up to two seconds without forcing a second cancellation. One deleted/unavailable history record cannot prevent cancellation of other tasks. It returns the pending-owned-task count; **keep MCP/history/event loop alive while that count is nonzero** and call close again after cleanup progresses. A pathological blocking SQLite/provider/caller is not a hard real-time guarantee. Completed cleanup is not automatically forgotten merely because the two-second wait expires. Do not recover or independently write/delete live histories through another coordinator; the deletion regression only verifies defensive teardown.

`test_chat_target_tasks.py` uses actual stdio production MCP with synthetic readers and fake providers. Twelve authored cases cover immediate Stop, exact/concurrent retries, frozen caller IDs, running cancellation, completion-versus-Stop, slow cleanup, close during fresh admission, overload before acceptance, outsider ownership, queued preclaim failure/retry/cancel, caller cancellation and deleted-record teardown. No inference/key/game is needed for these tests.

`dev/verify_tiles.py` additionally completes the getter-backed original tile question through this task owner after original token eviction, then cancels one deliberately pending fake provider in a second chat through the actual copied-game MCP lifetime. Repeat starts do not add provider calls, terminal cleanup finishes, newer chips survive and the tile-request mailbox stays unchanged. Normal tile/scene/reload checks, clean game exit and copied-mod/save restoration remain required. [Evidence](CHAT_TARGET_TASKS_VALIDATION.json) pins final sources and the finite scope. This is helper backend acceptance, not native controls, physical play, all scenes or a fresh real-Pro/player release.

## Completed local Claude review

A bounded local Opus/high source critique completed on actual `claude-opus-5-5` (46083 ms, one reported turn). Its queued preclaim failure concern produced owned queued cancellation and an explicit regression, including the done-task/before-callback case. Its deleted-record teardown concern produced per-record defensive cancellation so remaining tasks are still observed/owned. Independent checks added active request-ID reuse refusal and recent-cache intent hashes. Final changes are independently tested, not re-reviewed.

The proposed post-commit scheduling gap does not exist in the supplied owned admission path: no await occurs after the queue transaction returns and before registration. Pending admission cancellation remains an explicit caller operation, and the future native flow must integrate it. The proposal to clear remote uncertainty merely because local failed/cancelled status is terminal was rejected: local stream cancellation/failure cannot establish remote receipt/billing/cancellation. No credits or account-limit bypass occurred. [CLI metadata](CLAUDE_UX_COLLABORATION.json) pins reviewed input separately from final follow-up.
