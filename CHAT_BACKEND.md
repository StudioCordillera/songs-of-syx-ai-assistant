# Experimental chat implementation

This development implementation adds a shared local conversation engine, private SQLite histories, a native DeepSeek API adapter and an opt-in mod-owned GUI. It does **not** complete the acceptance gates in [IN_GAME_CHAT.md](IN_GAME_CHAT.md). OpenAI/Claude adapters, in-game account setup, installation without a terminal, richer transcript navigation/export/delete and broad menu/lifecycle coverage are pending. No authenticated inference has been performed.

## Development launch

Install the Python project in a virtual environment (`pip install -e '.[dev]'`). Use the same `SYX_STATE_DIR` as the game exporter. Set `DEEPSEEK_API_KEY` in the coordinator's environment through your local credential setup; do not put a credential into chat, a committed file or game launch arguments. Start:

```sh
syx-chat --state-dir "$SYX_STATE_DIR"
```

The default history directory is `~/.local/share/syx-assistant-chat`, separate from game exports and saves. `--history-dir` overrides it. The coordinator currently requires Linux/POSIX file locking; Windows support is pending. Only one coordinator can own a history directory. Stop it with Ctrl-C. Stopping cancels active replies; restarting marks interrupted turns and never automatically resends them.

Build/install the development mod using [INSTALL.md](INSTALL.md). Add the Java property `-Dsyx.assistant.chat=true` to the game launch configuration to enable the experimental panel. It is off by default. The panel has an **AI chat** launcher, chat list, transcript, composer, Add text, Send, Stop and explicit Attach to this game. New chat uses the current composer text as its name, or “New chat”. Select a chat before sending. Continuing after a reload requires Attach to this game. Model/account selection is not yet exposed; new chats use `deepseek-flash` through the DeepSeek API.

The composer is a bounded native single-line widget. Add text appends short segments into a draft up to 8000 characters; Send submits that draft plus the current segment. This is a prototype interaction, pending a proper multiline editor. The panel previews the latest 100 events, bounds text per event and limits rendered rows. Preview omissions are labeled; original bounded events remain in SQLite. Tool evidence is currently shown as plain text, pending expandable evidence and citation widgets. Full history is retained until explicitly deleted through future UI controls; there is no automatic retention/deletion policy yet. Do not treat the prototype as a finished daily-use client.

## Architecture and limits

`syx_chat.py` uses a provider-independent loop with exactly the existing 13 allowed MCP tools and requires their read-only annotations. It inspects fresh game status before each turn and before each tool observation, rejects a different runtime session, preserves provenance/tool errors and bounds requests to eight provider rounds, sixteen tool calls, 64 KiB per tool response and 180 seconds per turn. Models still need to select relevant fields and cite evidence: the code cannot guarantee answer quality or citation correctness. Quota/authentication/network errors never trigger a different provider or billing route.

`syx_deepseek.py` implements HTTPS streaming, fragmented function calls, explicit completion checking and bounded responses against the pinned official endpoint. `deepseek-flash` and `deepseek-v4-pro` are explicit supported model identifiers in the adapter; the panel currently exposes the former only. Requests enable thinking with high effort and an 8192-token output cap. The official [DeepSeek thinking/tool protocol](https://api-docs.deepseek.com/guides/thinking_mode/) requires private continuation from previous assistant turns when tools are provided. That data stays in memory and is excluded from stored events. A restart or failed/cancelled reply discards it and logs a context reset; earlier visible conversation is then quoted as bounded historical data in a new provider context. This is not exact provider-state restoration. Streaming behavior follows the official [chat completion reference](https://api-docs.deepseek.com/api/create-chat-completion/).

`syx_chat_store.py` keeps chat UUIDs, runtime-session attachment, turn UUIDs, statuses and timestamped events in SQLite with foreign keys and transactions. Configured credential strings are redacted, including across visible stream fragments; known credential metadata and hidden-reasoning fields are excluded. This is not a detector for arbitrary secrets pasted by a player. Histories contain private conversation/game evidence in plaintext on the local disk; permissions restrict the directory/database to the user. The database is not encrypted. Unknown schema versions are rejected.

`syx_chat_service.py` owns a single-writer lock, explicit cancellation, a durable action-admission journal and atomic bounded local file IPC. An interrupted/admitted action is not replayed automatically; the user may need to select an already-created chat or start a new action after checking history. Request and turn UUIDs prevent accidental resubmission of the same request. The MCP child does not receive the configured provider credential in its environment. No TCP listener is opened. Network inference runs in the Python coordinator; game APIs are accessed only by the existing in-process bridge.

`ChatPanel.java` uses source-verified public game widgets and a separate, non-disturbing public GUI section. It does not replace the game's shared section/popup. The game GUI manager routes real input to the mod's own controls and consumes owned clicks. The panel does not call the game's input-dispatch functions; only the isolated test fixture does. It does not consume the game's Escape shortcut. The existing I/O worker exchanges detached strings with the coordinator; GUI operations stay on the game update thread. A snapshot exposes the mod-owned panel's open state and selected chat as `ui_context.assistant_chat`, separate from underlying game selection. These public GUI members are source-verified APIs, not established stable official contracts. Pinned/modal ordering, keyboard behavior, scaling, reloads and standalone menus require more validation.

## Evidence

See [CHAT_VALIDATION.json](CHAT_VALIDATION.json) for the tested revision and explicit limitations. Offline protocol tests use mocked inference; a real local MCP subprocess test verifies the tool set and missing-game refusal. The isolated copied-save game fixture checks own-widget click consumption, composer focus, chat creation through the coordinator, missing-key refusal, reopen identity and world/city transitions. It does not establish physical keyboard behavior, full menu coverage, live account authentication, real answers, cancellation during paid inference, or provider-independent product completion. Earlier game-observation evidence in `validation-evidence.json` remains identified as the 0.12.0 baseline and must not be interpreted as a rerun of all scenes with this prototype.
