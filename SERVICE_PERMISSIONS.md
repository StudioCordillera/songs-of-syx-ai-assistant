# Configured city service permissions — game 0.71.44

`services /access_policy` reads registered public `RoomServiceAccess` types, their associated statistics' `permission()` interface, and `is(HCLASS_RACE.clP(race,class))` for concrete installed race/class pairs. Production calls no permission setter, service access request, reporting method or finder. The returned boolean is named `allowed_by_configured_rule` to distinguish configuration from actual individual eligibility.

The inspected source implements the flag through an internal inverted bitmap, but the adapter never accesses that bitmap or the private implementation type. It calls the public returned boolean interface. `HCLASS_RACE.clP` returns the initialized cohort object; null-race/class aggregate selectors are excluded. These are shipped-source-verified public APIs, not separately documented stable mod contracts.

The same source's `accessRequest` applies additional rules: nobility/tourist types can bypass the configured cohort flag, while child/parent-type paths can use a parent's class and require a child-appropriate standing definition. That method is not invoked or reimplemented by this collector. A configured false flag does not prove every individual of the visible class is barred, and true does not prove reachability, available service points, demand or a successful visit. Existing selected-person service statistics remain separate observed attributes.

`service_types` lists service ID, blueprint ID and installed room-help reference. A registered type can have no built room. `cohort_rules` contains service ID, blueprint ID, race/class keys and the configured flag. Service IDs are load/session scoped; join them to `service_types` in one observation. Blueprint IDs can join per-room service counters, producing multiple instances. Race/class keys can join population cohorts; this does not turn configuration into a census or individual eligibility decision.

The reader caps service scans at 256, rule rows at 10,000 and both race/class scans at 64. It emits each service's complete cohort batch or omits it on failure/cap, with truncation, failed-type counts and ten bounded failure samples. Missing rows are unknown, not denial. Battlefield defaults are suppressed as unavailable city policy; world setup has an unavailable services domain. A known scene and same-observation context are required when using these values in advice.

`service-policy-query-example.json` joins configured denials to population. Joining on race first requires the explicit class-equality filter; omitting it would multiply mismatched cohorts. This query returns at most five rows and shared UI context. It deliberately does not label those population counts as the number of people actually prevented from using a service.

The isolated copied-city fixture sets two policy flags through the public interface to establish both true/false cases, then waits for a later collector sample. It never saves. Those setters exist only in development tests. The production observer is read-only. SERVICE_VALIDATION.json pins getter/paging/query agreement, limits and source evidence; finite scene checks do not establish every menu, every service type, cap/failure injection or large-city cost.
