# Stored producer-room degradation — game 0.71.44

`production /room_data/flows` includes `room_degradation_raw`, read once per included producer room through public `RoomInstance.getDegrade()` and repeated on that room's recipe resource rows. It is a dimensionless stored normalized degradation value. Finite values are preserved without clamping; nonfinite values become null. Do not sum this factor across flows, and do not treat flow counts as distinct room counts.

The shipped base getter decodes stored wear with a threshold. Zero does not prove no wear or no maintenance need: initial stored wear is hidden below that threshold. It is not remaining durability, instantaneous productivity, required maintenance resources or a full production multiplier. Exact last wear/maintenance time remains unknown. A current observation does not make the stored wear a fresh calculation. Use same-observation room IDs to join staffing and recorded recipe/ledger data, and retrieve installed room help. Room IDs may be reused; they are not permanent or UI-selected identities.

The adapter reads only producer `RoomInstance` objects. Static shipped-source review also identifies a final non-producer chamber override with different display semantics and a construction sibling getter that writes a shared delegate. Neither is part of this mapping. The adapter obtains no degrader handle and calls no maintenance, update, report, refresh, generic employee-list or production-rate helper. Third-party overrides may change meanings and costs; review evidence is for the pinned shipped implementation, not arbitrary mods.

Existing production limits remain 2,000 flow rows and 10,000 room scans, with atomic recipe batches and bounded failure diagnostics. A failed room is omitted and counted; null/unavailable/skipped data does not imply zero degradation. Completing pagination does not establish complete city coverage. Setup without a settlement is unavailable; battlefield observations describe scene-local producer rooms if present, not campaign room conditions.

`degradation-query-example.json` projects recorded output rows, degradation and nullable staffing, sorted by degradation. This can help choose questions to investigate; it does not establish why a room produces a particular quantity. The same room value is repeated for multiple resource outputs. A missing staffing join stays null.

DEGRADATION_CONTRACT_REVIEW.json pins the public base getter chain, stored decoder, bit reader and excluded override findings through static source/binary inspection. Private storage/implementation details are inspected only in licensed files, never read directly by the mod. DEGRADATION_VALIDATION.json and PLAYER_CORE_VALIDATION.json pin finite copied-game getter/MCP checks, value counts and query parity. Public source verification is not a separately documented stable mod contract, complete bonus model, large-city benchmark or exhaustive room/scene acceptance.


The native fixture also supplies five fixed encoded inputs to public `ROOM_DEGRADER.get(int)` to test zero, threshold, first positive, half and maximum values. These are synthetic decoder cases, not wear read from five rooms. It never writes encoded values into room storage. Actual producer-room positive/zero counts are recorded separately; a zero-only city does not establish nonzero room integration or meaningful ordering across different room values.

Reproduce the static boundary review with `dev/verify_degradation_contract.py --game-dir <licensed-game> --jdk-home <jdk> --output <report>`. The standard `dev/verify_current_player_core.py` copied-save runner includes this native fixture and publishes its degradation results under the production check. It accepts `--candidate-dir` and a matching `--validation` provider report for testing without replacing the published ZIP. Use only an isolated fixture profile and a copied save under runtime; no game/source binaries or saves are redistributed.


DEGRADATION_POSITIVE_VALIDATION.json adds a separate controlled integration check. The test-only `DegradationPositiveScenario` invokes public `MAINTENANCE.vandalise(int,int)` on one producer in a disposable paused copied game until its getter becomes positive, with at most 512 calls. The existing production verifier independently checks actual MCP flow values and sorted nullable-staffing selection against the native getter fixture. No game is saved, and this action is never packaged or exposed through the production mod/MCP. The baseline city still has 16 zero-valued producers; controlled positive evidence does not establish natural wear, every room type, maintenance cost or an actual production-output effect.

To reproduce this additional case, use the isolated copied-save `LiveSmoke` harness with `-Dsyx.smoke.degradationPositive=true` and run `dev/verify_degradation_positive.py --state-dir <isolated-state-dir>`.
