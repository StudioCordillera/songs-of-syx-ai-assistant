# Candidate chat layout preferences

This is an unshipped extension of the [native layout candidate](NATIVE_CHAT_LAYOUT.md), authored by Codex using earlier completed Claude findings. No new Claude source review is claimed: an existing local CLI process was not established idle. The production constructor, tested player JAR/ZIP, normal profile, saves, key and histories remain unchanged.

The candidate has an explicit `configureCandidatePreferences` seam for a caller-owned directory. The fixed native fixture configures only its disposable runtime directory. There is no automatic production path, per-world identity, history migration or new MCP/action tool. A developer-only startup property now allows the fixed runner to supply the same private directory across two actual copied-game launches; the released panel does not consume this property. Future player integration must choose the private stable configuration directory and validate restart/multiple-load behavior before shipping.

`PanelPreferences.java` reads legacy version 1 geometry and version 2 geometry/style records. Version 1 has eight integer panel/launcher coordinates and dimensions; version 2 adds a known preset and canonical uppercase `#RRGGBB` accent in `chat-layout.preferences`. No question, transcript, session, provider, key or target is stored. The legacy constructor still emits the original geometry-only version-1 bytes; the configured candidate panel writes version 2. Each file is at most 512 bytes; coordinates are 0..8192 and dimensions 1..8192. Duplicate, missing, unknown, non-ASCII, malformed and unsupported-version fields refuse the entire record. Geometry is fitted to the current accepted internal viewport on loading, retaining the candidate's minimum/fallback policy.

Explicit gesture drops, Reset and valid style choices write preferences when the candidate directory is configured. Without it, style changes stay in memory and say so. Automatic viewport clamping, helper refresh, opening and closing do not write them. A smaller display therefore does not silently overwrite the saved layout. Loading is bounded through a non-following channel; missing files use the current defaults, while malformed files preserve current geometry and remain untouched. Reset can explicitly replace malformed preferences after the directory has been successfully configured. A failed save leaves the changed layout usable for this run and shows a plain notice; a failed load also shows a notice. No automatic retry loop or blocking file operation on every update is added.

Saving uses a private mode-0600 temporary file in the same existing directory and atomic replacement, with cleanup on failure. Unsupported atomic moves/POSIX permissions refuse rather than falling back to a partial overwrite. Static file/directory symlinks and nonregular files are refused; replacing a regular hard link leaves its other link unchanged. These finite checks do not establish a hostile concurrent filesystem/race-security boundary, crash/power-loss durability, all-filesystem portability, non-Linux support or universal game-thread I/O cost. The caller must own and protect the configuration directory.
